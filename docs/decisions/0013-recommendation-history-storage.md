# ADR 0013: Recommendation snapshots and generated history

Status: engineering implementation for the authorized Day 3 backend slice. No new dependencies or training rules.

Use `recommendations.sqlite` schema 1 separately from setup, practice and manual stores. Preserve immutable, self-contained schema-1 prescriptions even when the application's current program changes. Program/rule/catalog versions are provenance, not an instruction to rewrite a historical prescription. Unknown snapshot schemas reject reads. Store ordered slots and ordered work/rehearsal targets, paired-block identities, side, exact load convention, setup revision, baseline revision reference, rest, reps, RIR and bodyweight range reference. Store generation input revisions, history revision, reasons, evidence references, requested civil date and timezone. Missing/blocked results are stored without executable targets.

The storage boundary validates structure, not scientific approval. Only future guarded composition may supply executable snapshots; this slice has no production UI/composer caller and does not activate a catalog. Saving a snapshot does not verify its catalog, equipment or baseline. Fresh eligibility, setup, constraints and safety checks are still required by Day 4/5 orchestration before starting execution. Setup currently lives in its own database; cross-store atomic input capture is not claimed here.

Each profile has a monotonically increasing history revision. A recommendation pins that revision. Every session start, actual change and terminal transition advances it atomically with audited prior state and an idempotent action receipt. Unstarted recommendations at an older history revision are stale and cannot start. This conservatively invalidates all unstarted calculations for that profile, including calculations using an empty history. Active and historical prescriptions remain unchanged. Evidence names explicit session revisions; saving rejects unknown or superseded evidence.

Sessions have contiguous per-profile sequence numbers, one active session per profile and one occurrence per recommendation. Record one actual per prescribed slot/set/side/phase. Terminal completion requires every working target to have an actual or explicit skip; ended-early preserves partial evidence. An interrupted active session remains active. Corrections replace one current record, retain its predecessor and cannot change prescription, sequence, start or terminal state. Correction cannot erase a previously reported pain stop: affected slots remain flagged for future safety orchestration. No reset behavior is invented here.

The progression adapter reads one consistent complete repository snapshot, never caller-filtered manual/practice data. Stable program IDs scope occurrences across versions; intervening other versions or a historically missing slot remain nonqualifying exposures, rather than disappearing from a streak. Reads verify the entire audited transition chain before supplying evidence. It keeps every occurrence of the scoped program/session/slot, including incomplete, skipped, different variation/setup/baseline and corrected exposures. Exact setup revision, convention, prescription and confirmed-baseline reference must match before an exposure can qualify. Warm-ups are excluded; each corrected working record is counted once. Global occurrence sequence permits gaps for other slots. A baseline reference denotes one immutable confirmation revision; reconfirmation must use a new reference even at the same load. Mixed variation working sets remain unsupported pending policy.

Format bounds are defensive: IDs 128 characters, 100 slots, 1000 targets per slot, payload 2 MB, integer millionths of pounds up to 1,000,000 lb, reps/RIR up to 10,000. These are not training recommendations. SQLite foreign keys, relational/payload consistency checks and parameterized values protect references. Transactions preserve old data on conflicts/failures; unsupported database versions refuse to open. Export/deletion later must cover all four databases. No migration from manual history or real user values is performed.

## Verification

Passed 278 unit/widget tests and seven actual SQLite tests on the owner-authorized iPhone 17 Pro simulator; formatting and static analysis passed. Native tests use only `recommendation_history_fixture.sqlite` with `--no-uninstall`. No real owner measurements were seeded. The expected unsupported-schema fixture emits a generic refusal message. Existing package notices report four newer releases outside the lockfile constraints; no dependency changes or dependency-security audit are claimed. Physical-device and process-termination/power-loss checks remain separate acceptance work.
