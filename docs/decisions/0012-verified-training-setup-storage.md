# ADR 0012: Local training-setup snapshots

Status: implementation decision for the owner-authorized Day 2 work. No new dependencies.

Use a separate `training_setup.sqlite` store, leaving practice and manual-program databases untouched. Schema v1 keeps one current immutable aggregate per profile plus every prior revision and transactional action receipts. The aggregate contains explicit calendar/duration preferences, unknown-or-explicit capability/limitation assessments, equipment/setup observations and exact starting-load confirmations. Unknown assessments are never interpreted as clearance.

Equipment confirmation is owner attestation about a named physical setup, not clinical or catalog review. Each setup has a revision, an optional approved taxonomy equipment ID, exact load convention, available work/rehearsal settings, quantity, item-scoped capabilities and explicit confirmation time. Starting loads reference the exact program session/slot, variation key, setup ID/revision and convention. The variation keys in the setup coverage registry are preparation identities, not reviewed catalog IDs; no record is fed to recommendations in this slice. Missing catalog bindings remain explicit. No approximate or conversation-derived load is seeded.

Store pounds in integer millionths; reject fractions beyond six decimal places, exponents, nonfinite and negative values rather than rounding. Defensive storage bounds: up to 1,000,000 lb, 100 setups, 500 starting-load records, 1,000 unique settings per ladder, 120-character labels and 128-character printable identifiers. These are format limits, not physiological recommendations. Positive whole-minute duration preferences have no 45/75-minute training cutoff; use a 32-bit integer storage bound. Duplicate list entries are rejected before sorting. Equipment quantities/capabilities use existing taxonomy bounds. Bodyweight has no numeric load; assistance is separate from added weight. Zero is permitted only in the rehearsal ladder for an external-load machine.

A saved baseline requires exact owner confirmation and a matching confirmed setup; its value must exist in that setup's working ladder. Context changes invalidate reuse: an old baseline referencing an earlier setup revision stays historical and is flagged stale. Reconfirming it writes a new aggregate revision. Unknown taxonomy equipment IDs are rejected; missing ones may be stored as pending catalog mapping, never inferred from a label. Source catalog review and exact setup verification remain independent.

Every write checks the expected aggregate revision, preserves its predecessor and writes an idempotent receipt atomically. Same action/same canonical payload returns the original receipt; changed payload conflicts. Reads validate JSON and relational ID/revision agreement. Unsupported schemas fail without clearing files. V1 creation is transactional; no older adaptive schema exists to migrate. Forward migrations require explicit fixtures before a future schema bump. UI acknowledges success only after write and reload; failed acknowledgement retains the action for safe retry.

Tests cover validation, exact decimal parsing, references, stale setup revisions, retry/failure UI state, actual SQLite reopen/rollback/receipts/corruption/unsupported versions. The owner authorized simulator review: all four native storage tests passed on the iPhone 17 Pro simulator, and the regular app was launched for owner inspection. All 267 unit/widget tests, formatting and static analysis also passed. This is not physical-device acceptance or a power-loss test. Catalog coverage/review remains pending; no approval stamps are synthesized.
